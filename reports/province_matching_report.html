A methodology bug was caught and fixed here

The first version of this crosswalk matched each ATT_PROVINCE_ID to a province via the leading 2 digits of its records' postcodes, assuming that prefix equals the province geocode. That assumption silently breaks for Bangkok/Samut Prakan: Samut Prakan has no postal block of its own -- its real postcodes (10270, 10280, 10290, 10540, 10560, ...) fall inside Bangkok's 10xxx block -- which shifted every subsequent province's postcode prefix one behind its geocode across the entire Bangkok-Samut Prakan-Nonthaburi-Pathum Thani-Ayutthaya-Ang Thong-Lopburi- Sing Buri-Chai Nat-Saraburi block (geocodes 10-19). The result was two different ATT_PROVINCE_IDs both resolving to Bangkok, and Saraburi ending up with no id mapped to it at all. Caught by checking for duplicate province_id assignments across the crosswalk (there should never be two), not by re-running more postcode logic. Fixed by resolving each postcode against a real postcode→province reference table (kongvut/thai-province-data) instead of assuming a prefix match, then re-validated: every one of the 77 provinces now has exactly one ATT_PROVINCE_ID mapped to it, with zero duplicates. See tests/unit/test_tat_crosswalk.py for the regression guard and scripts/validate_tat_crosswalk.py for the independent validation below.

What is TAT's 78th value?

77 of the 78 distinct ATT_PROVINCE_ID values follow the "10XX" pattern and were matched to a real province via a real postcode→province reference (75 automatically; the remaining 2 -- 1005 and 1045 -- had no usable postcode anywhere in their records and were hand-identified by searching their attraction names, resolving to Kamphaeng Phet and Yasothon respectively). The 78th value is the literal string "1", attached to 13 of the file's 1731 records (0.75%). Their names are junk/placeholder data -- "test", "test 13120844", "Hello world!" (three times) -- not a real 78th province. It reads as an unset/default province_id sentinel in the source system, a concrete data-quality defect in a government open-data file, and is excluded from the crosswalk rather than assigned anywhere.

What are flood's 2 missing provinces?

thailand_flood_risk_areas.csv has rows for 75 of the 77 provinces. Diffing its (prefix-stripped) province list against the master shows the 2 entirely absent provinces are Phuket (ภูเก็ต) and Ranong (ระนอง) -- there is not a single row, for any tambon, in either province, across all 17 years the file covers. This isn't a spelling mismatch (every other province matches exactly once its "จ." prefix is stripped; Bangkok is the one province stored without that prefix).

Why they're absent, and why that's not the same as "zero risk": this file measures recurrent floodplain risk, which is river-basin derived. Phuket is an island with no major river basin; Ranong is a narrow coastal strip pinned against mountains. Neither has areas that meet this file's definition of flood-risk terrain -- but both experience real flash flooding, and Ranong is the wettest province in Thailand. Treating their absence as "0 risk" would tell any model built on this data that they are safe, when the honest statement is "unmeasured by this method."

Business rule for dim_geography (Phase 3): Phuket and Ranong must map to the Unknown Member (sk = -1) for every flood attribute sourced from this file -- never imputed as 0, never classified as low risk. A flood_data_available boolean column should accompany the flood attributes so the dashboard can show this distinction honestly rather than silently. Phuket in particular is a major tourism province, so this directly affects BQ2 (rain/flood premium loading) and BQ4 (tourism-dense province risk profile) if not handled this way.
